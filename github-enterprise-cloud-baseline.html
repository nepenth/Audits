What this baseline is for

The organization is moving source code and pipelines from Azure DevOps and GitLab into one GitHub Enterprise Cloud enterprise that uses Enterprise Managed Users. This page states how that enterprise should be configured, and gives a checklist to audit the live configuration against it. Each control cites the documentation or guidance it rests on. Where a statement is our own judgement and not a vendor recommendation, the text says "our position".

Principles

Set the floor as high in the hierarchy as it will go

GitHub's guidance is to use enterprise policies to enforce business rules, because each enterprise policy limits what organizations can choose below it. Since 2025, rulesets and custom properties also work at the enterprise level. Our position is that anything every repository must have belongs in an enterprise policy, an enterprise ruleset or an enforced security configuration. Organization and repository owners can add protection and cannot remove the floor.

EnterpriseIdentity, network and token policy. Member privileges. Baseline rulesets. Actions policy. Default security configuration. Audit streaming. AI controls.
OrganizationTeams from IdP groups. Tier rulesets targeted by custom property. Runner groups. Organization secrets. App installations.
RepositoryCODEOWNERS. Required checks. Environments and their reviewers. Extra rules a team chooses.
WorkflowExplicit permissions. Locked or pinned actions. OIDC for cloud access.

Classify repositories, then target rules by class

Required custom properties with defaults (tier, data classification, owning team, compliance scope) let one small set of rulesets cover every repository correctly. This replaces naming conventions and hand-maintained lists, and it gives the migration a simple job: set the properties when a repository lands.

Identity comes from the IdP and nowhere else

With managed users, accounts, group membership and offboarding are IdP events. People get access through teams synced from IdP groups. Automation uses GitHub Apps and OIDC. Personal access tokens are the exception: fine-grained, approved and short-lived.

Treat CI/CD as production infrastructure

The supply chain incidents of 2025 and 2026 (tj-actions, Nx, trivy-action, TanStack) worked by getting code to run inside pipelines that held credentials. GitHub's response during 2026 was a set of enforceable controls: SHA pinning policy, workflow lockfiles and workflow execution protections. This baseline adopts those, defaults the workflow token to read-only, and replaces stored cloud keys with OIDC.

Evaluate first, then enforce

Rulesets and workflow execution protections both have an Evaluate mode that reports what would have been blocked. New rules start there, insights are reviewed, then the rule becomes Active. During migration this matters twice over, because some rules can make imports fail.

Prefer generally available features; track previews

Controls marked Preview are worth knowing about and often worth piloting. They are not required for a compliant result, and their behaviour may change.

Order of work

  1. Identity and break-glass. IdP, SCIM, group model, setup user vaulted (ENT-01 to 03, IAM-01 to 04).
  2. Visibility. Audit log streaming and core detections, before any real content arrives (LOG-01, LOG-05).
  3. Enterprise policies. Member privileges, token policy, Actions policy, security configuration as the default for new repositories (POL, IAM-07, ACT-01 to 06, SEC-02).
  4. Classification and rulesets. Custom property schema, baseline ruleset in Evaluate (POL-10, RUL-01).
  5. Platform repository. Shared workflows, runner groups, OIDC trust pattern (ACT-08, ACT-09, ACT-15).
  6. Rehearse. Trial migrations into a sandbox organization with the same governance (MIG-02, MIG-03).
  7. Migrate in waves. Set properties and apply configuration per batch; reclaim mannequins; convert pipelines (MIG-04 to 08).
  8. Tighten. Move rulesets to Active, add metadata and push rules, restrict deploy keys, require lockfiles (RUL-11, RUL-12, POL-09, ACT-03).

Decisions the organization still has to make

  • How many organizations, and what the boundary between them means (ENT-04).
  • Whether new repositories are private or internal by default (POL-11).
  • Which security products are licensed and what covers any gap (SEC-01).
  • Whether to use an IP allow list, and how runners will reach the enterprise if so (IAM-06).
  • Whether forking is allowed inside the enterprise (POL-03).
  • Maximum token lifetime and who approves tokens (IAM-07).
  • Evidence retention period for build and deployment records (ACT-11).
  • Whether Copilot and third-party agents are in scope, and for whom (AI-01, AI-02).

How to run the audit

  • Work through the Audit checklist tab with an enterprise owner account, or a custom role that can read enterprise settings and policies.
  • For each control, compare the live setting with "Recommended" using "How to check", choose a status, and record what you saw. Use Accepted risk only with a named approver in the notes.
  • Navigation labels in GitHub change often. If a path here does not match, search the settings page for the policy name and note the new location. API hints should be checked against the current REST reference before scripting.
  • Export the audit as JSON when finished and store it with the audit record. The export can be re-imported into any copy of this page.

What the repository importer does and does not carry

  • From Azure DevOps: Git history, pull requests with their history, work item links and attachments, and repository-level branch policies. Not carried: Git LFS objects, user-scoped and cross-repo branch policies, pipelines, boards, service hooks and permissions. Only Azure DevOps Services (cloud) is a supported source.
  • From GitLab: Git history, wiki, issues, merge requests as pull requests, milestones, releases and members as placeholder users. Not carried: Git LFS objects, approval rules and other project policies, group settings and membership, CI/CD pipelines, variables, webhooks, vulnerability reports, snippets and boards.
